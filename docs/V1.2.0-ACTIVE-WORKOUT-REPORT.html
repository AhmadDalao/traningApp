2. Start, train, resume, finish

Two supported flows

Quick:    Planned → Mark completed → Existing saved workout
Detailed: Planned → Start workout → Log sets → Finish workout → Set history
  • Start: Only an owned, planned training session can start. Rest days and completed/skipped sessions cannot. Start captures a frozen prescription and independent media copies, creates session exercises and empty actual set fields, then records the server start time.
  • One active workout: A user row lock serializes starts. Attempting a second workout redirects to the existing active one with a clear message. Repeated Start reuses records and the original start time.
  • Resume: Overview has a resume reminder even when the active session was scheduled on another date. Session Details shows In progress and Resume workout. Calendar events still open ordinary Session Details.
  • Persistence: Complete/save a set, edit a completed set, save a draft, add/remove a set, skip/undo an exercise: each saves immediately. Typing alone stays local. Unsaved inputs are labelled, finish asks the user to save them, and adding/removing/renumbering other sets preserves them.
  • Reps: Completing a reps set requires a positive integer actual rep count. Weight is optional, supports decimals and can be zero. A planned weight is offered as an editable visual default; initial database actuals remain empty until the user saves.
  • Duration: Actual time is entered as mm:ss and stored as integer seconds. Invalid values such as 00:60 are rejected. The existing exercise editor now has Reps / Duration under Track by; new exercises default to Reps.
  • Set controls: Completed sets remain editable during the active workout. Editing retains the completion timestamp; marking incomplete clears it but keeps results. Add Set copies only planned targets. Remove affects only this session, asks confirmation for completed sets, then renumbers.
  • Exercise controls: All existing sets done makes the exercise Completed. Making a set incomplete or adding another returns it to Active. Skip retains sets/results, asks confirmation if any sets are completed, and can be undone. Superset A/B/etc. remains a visual grouping.
  • Finish: The server checks incomplete sets in unskipped exercises. Explicit confirmation allows finishing with incomplete work. No missing results are fabricated. Completion time and elapsed minutes are saved; the existing calorie estimator uses that duration, intensity and dated body weight. Reported calories are retained.
  • Discard: Confirmation removes only this active session’s detailed exercises/sets and clears started_at. The plan, scheduled session and frozen prescription/media remain. The session is Planned again.
  • Rest timer: 60, 90 and 120 seconds; Start, Pause, Reset. Browser-only state, independent of set logging and session status. Leaving the page may reset it.

Elapsed minutes use the nearest whole minute, minimum one. Completed session details keep optional manual duration/intensity/calorie editing.

3. Architecture and database

The application remains one Laravel monolith, connected to React through normal authenticated Inertia web routes. Existing status values remain planned, completed and skipped. In progress means a planned training session with non-null started_at.

TrainingPlan → TrainingDay → TrainingExercise        reusable prescription
User → ScheduleEntry → session_exercises → session_sets     actual workout
                    ↳ workout_snapshot                     frozen prescription/media

One additive migration

2026_10_27_000007_add_active_workouts.php is applied locally and on Hostinger. It adds nullable schedule_entries.started_at, nullable training_exercises.tracking_mode, and two new tables. It updates no existing rows and creates no historical logs.

TableFields and relationships
session_exercisesid, schedule_entry_id, nullable source_training_exercise_id and source_exercise_key, name, tracking_mode, planned_sets, planned_reps_text, planned_weight_kg, superset_group, thumbnail_path, custom_icon_path, icon, notes, position, status and timestamps. Status is Active / Completed / Skipped. Unique session+position. Deleting the session cascades; deleting a source template only nulls its optional FK.
session_setsid, session_exercise_id, set_number, planned_reps_text, planned_weight_kg, nullable actual_reps, actual_duration_seconds, actual_weight_kg, completed_at and timestamps. Unique exercise+set_number. Deleting the session exercise cascades to its sets.

Backend responsibilities

  • ActiveWorkout: start/copy, shared parent-row lock for mutations, add-set targets, finish/duration/calories. The user lock prevents simultaneous starts on two sessions.
  • ActiveWorkoutController: Start, Show/Resume, Finish and Discard.
  • SessionSetController and UpdateSessionSetRequest: validate and persist actuals, completion and removal.
  • SessionExerciseController: skip/undo and Add Set. Ownership is authorized through the existing ScheduleEntry policy on every route.
  • Session Details and History eager-load exercises/sets. History list loads aggregate counts instead of per-set result rows.

4. Historical integrity and compatibility

  • Source priority is existing session_exercises, then an existing workout_snapshot, then the current linked Training Day. Starting does not replace preserved history with a newer template.
  • New snapshots remain version 1 with additive tracking_mode/source_exercise_key fields. Existing snapshots are neither rewritten nor backfilled.
  • Built-in library keys are copied exactly; private custom exercises use their stable custom:ID key. Manual/older exercises can have null identity. Identity is not inferred from the name.
  • Media is copied into the existing snapshot storage at start, so editing/deleting the training template cannot remove workout media. Session exercises reuse those preserved media paths. Deleting a session cleans its snapshot media and cascades its logs.
  • Quick completion creates no fake session sets. Legacy completed sessions without snapshots continue to show the existing historical notice.
  • Detailed history displays saved sets, incomplete results and skipped exercises. Quick/legacy history retains the old actual-weight editor. Backend rejects the one-weight-per-exercise endpoint for detailed workouts.
  • Ordinary status changes cannot bypass an active workout. Finish or discard it first. Reopening a finished workout preserves its logs/snapshot, clears started_at, and lets Start begin a new timing interval; it does not create duplicate sets.
  • Authentication, plans, library/custom exercises, icons, thumbnails, supersets, weekday scheduling, calendar, history periods/type/status/plan filters, default 10 rows, goals/recommendations, body-weight history, Progress and calorie behavior remain covered by the original tests.

7. Release notes, limits and next step

v1.2.0 is released. Production and the annotated GitHub tag contain the verified update. No v1.3 work has started.

For subsequent releases, retain the established Hostinger process: fresh backup of database/uploads/environment/files, deploy source and rebuilt assets, run the additive migration, rebuild caches, verify start/log/refresh/finish plus quick completion live, clean temporary QA/deployment files, then create the new commit/tag. Preserve previous tags and never use fresh migrations or seeders on production.

Deliberate boundaries

  • Legacy tracking_mode defaults to Reps, including old free-text duration prescriptions. Choose Duration explicitly in the editor for new sessions; old snapshots remain untouched.
  • Typing is not itself persisted. Use Done, Save changes or Save draft before leaving. The rest timer is intentionally not persisted.
  • Set results are edited while active; reopening a finished session reuses logs but begins a new elapsed-time interval.
  • The existing calorie estimator declines sessions over 24 hours. The existing duration column supports 65,535 minutes; a workout abandoned beyond that limit receives validation instead of a database overflow, and its logs remain intact.
  • No personal records, 1RM, volume/exercise charts, progressive overload, suggested weights, adaptive plans, per-set RPE, AI, nutrition or wearable APIs were added. These remain future releases.

No known blocking issue remains for the verified v1.2 workflows.
