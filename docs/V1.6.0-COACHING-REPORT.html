1. v1.6 summary

v1.6.0 adds a Coaching Workspace to the existing Laravel / Inertia / React application. Every account keeps personal training. Coaches gain consenting trainee connections, service packages, independent assigned plans, protected scheduling and read-only performance monitoring. The existing workout, History, Progress, PR and progression engines remain in use.

2. Updated account model

One users table, one password and one authenticated session. account_type is trainee by default or coach. Coach capability also requires an active CoachProfile. Account type and plan workspace fields are server-controlled, outside ordinary profile mass assignment.

A coach can receive coaching from other coaches. A trainee can accept multiple coaches. Self-coaching is rejected. There is no separate login, impersonation, organization or administrator model.

3. Registration flows

  • The existing registration page offers “I’m training” and “I’m a coach.”
  • Trainee registration preserves personal onboarding. Coach registration atomically creates the account and coach profile, then opens Coach Overview.
  • Coach display name is required; specialization is optional. Existing email/password validation, hashing, CSRF, session regeneration and login throttling remain.
  • Intended authenticated destinations are honored before default onboarding. Random training-code uniqueness is backed by the database, with bounded registration retries for a collision.

4. Workspace behavior

The avatar menu switches Personal Workspace and Coach Workspace without changing the logged-in user. A session preference controls the default landing page; route context determines authorization and which person’s data is queried. Separate tabs can therefore show different workspaces safely.

One authenticated actor
├── Personal routes: own training and My Coaching
└── /coach: templates, trainees and subscriptions
    └── /coach/trainees/{trainee}: authorized trainee context

Personal navigation keeps Overview, Training plans, Calendar, Training History, Progress and Profile, plus My Coaching. Coach navigation contains Overview, Trainees, Coach Plans and Subscriptions. The trainee banner supplies Overview, Plans, Calendar, History and Progress tabs.

5. Upgrade-to-Coach flow

Existing users open Profile → Enable Coach Workspace, enter a display name and optionally specialization/bio, and save. The update is idempotent and transactional. User ID, password, plans, sessions, goals and progress remain unchanged. The same screen edits an existing coach profile. No downgrade flow was added.

Existing production accounts remain trainee accounts until their owners choose to enable coaching. Their existing login credentials still work.

6. Training Planner ID

Every account receives a permanent TP- plus eight cryptographically random non-ambiguous characters. IDs are not derived from database IDs, names or email. Profile and My Coaching display the ID, with a Copy ID action.

Exact lookup normalizes case/whitespace and requires the complete code. Before consent it returns only a limited name and code; it does not return email, birthday, weight, plans or history. Connected-trainee search stays inside the coach’s own active relationships.

7. QR security

  • QR is generated locally as SVG using pinned qrcode.react 4.2.0; no remote QR service or in-app camera permission is needed.
  • A 256-bit random token expires after 10 minutes. Only its SHA-256 hash is stored. Generating a replacement invalidates prior unused tokens for that account.
  • GET opens a limited request page and never consumes the token, authenticates a user or grants training access. An explicit POST consumes it atomically when sending the request.
  • The addressed trainee must still accept. Expired, used, malformed and self-targeted links fail closed. QR responses use no-store and no-referrer headers.
  • Per-account and IP throttles protect lookup, request creation, token views and QR generation.

Dependency and license references: qrcode.react; the bundled generator’s MIT license. The ISC and MIT notices are included at public/licenses/qrcode-react.txt.

8. Coach–Trainee relationship model

coach_trainee_relationships records coach, trainee, requester, pending/active/ended status and timestamps. Only the addressed trainee accepts or declines; either participant may explicitly end a relationship. Participant locks enforce one open directional request/relationship per pair.

Acceptance explains that the coach can read training goals, body-weight progress, Calendar, workout history, exercise progress and PRs—including personal workouts and sessions from other coaches. It does not authorize logging results. Pending and ended relationships grant no trainee access. A reconnection creates a fresh consent cycle.

9. Subscription model

Coach-owned reusable packages define a name, optional description and optional duration. Starting a subscription snapshots its package name and inclusive start/end dates; a 56-day package ends 55 days after its start. Open-ended service requires an explicit selection. Notes are private coaching administration.

Subscriptions are active, paused or ended; effective access also accounts for future start and expiry. There is one open active/paused subscription per relationship. Pause and expiry preserve read access but remove management. Ending is confirmed. Changing or archiving a package does not rewrite an existing service period. No payment processor, billing or automatic renewal is included.

10. Coach Plan architecture

The existing training_plans table adds workspace_type: personal, coach_template or coach_assigned. The existing plan/day/exercise builder, library, icons, supersets and copy implementation are reused. Coach templates are excluded from personal lists, schedule pickers and progression template choices; crafted personal routes reject them.

Coach templates contain prescriptions and repeat weekdays/time. Assignment copies a template into the trainee’s ownership after confirmation of plan dates. A coach can also build a custom plan directly for an eligible trainee. Neither operation schedules sessions automatically.

11. Assigned-plan ownership

The trainee owns assigned plans, days, exercises, Calendar entries and every recorded result. Assignment provenance links the current relationship, originating subscription, optional source template and copied plan. Copies have their own IDs and media, retain exercise identity/tracking mode/supersets, and contain no copied workouts or results.

Source edits/deletion do not synchronize or delete copies. Private library identity survives an authorized copy without exposing the coach’s private library globally. The trainee may edit, duplicate or delete an assigned plan; a personal duplicate has no inherited coaching assignment. Coaches can edit their own active assignments or end them, but cannot delete the trainee-owned plan.

12. Schedule attribution

New sessions receive server-written scheduled_by_user_id; user_id remains the person training. Existing sessions retain null attribution rather than guessed ownership. Existing schedule_managed and unique occurrence keys remain the bulk-edit and duplicate guards.

The shared schedule preview displays Add, Keep, Remove, Protected and dates excluded by the effective subscription period. Confirmed actions revalidate a signed preview. Coach bulk changes affect only their own attributed eligible future sessions from their active assigned plan. Personal, other-coach, null-attribution, manual, detached, completed/skipped, active, saved/structured and historical sessions are protected.

Individual coach scheduling is also limited to eligible future sessions and service dates. It accepts only planned scheduling fields. Editing a generated occurrence individually opts it out of bulk management while retaining its original duplicate-prevention identity.

Owner policies remain owner-only. CoachAccess checks current relationship, effective subscription, assignment and source ownership. TrainingContext passes an explicit owner and URL prefix to shared controllers; it never changes authentication. Capability flags control rendering but never replace server authorization.

14. Disconnect behavior

Disconnect ends the relationship, its open subscriptions and active assignments under the same participant locks used for management writes. Subsequent reads and writes are rejected immediately. Plans, sessions, snapshots, set logs and progress remain with the trainee.

Reconnection requires fresh acceptance and does not revive old assignments or subscriptions. A renewal within an uninterrupted active relationship can manage that relationship’s still-active assignments, subject to the new effective service dates.

17. Migrations and indexes

One additive migration: 2026_10_28_000010_add_coaching_workspace. It adds the account fields, plan workspace category and nullable session attribution, then creates six tables: coach_profiles, coach_trainee_relationships, coach_pairing_tokens, coach_subscription_plans, coach_subscriptions and coach_plan_assignments.

Training IDs are backfilled in chunks before enforcing non-null. Existing passwords, IDs, timestamps and training columns are preserved. New uniqueness constraints cover code, coach profile, token hash and assigned-plan reference. Relationship/status, subscription/status and assignment/status composites serve the new queries. Inspected MySQL indexes showed no redundant single-column FK index alongside these composites. Existing exercise identity, ownership/date and occurrence indexes are reused; no speculative scale indexes were added.

Production migration completed with both existing accounts backfilled. All ten original application-table fingerprints match on their original columns. Local cleanup also restored the original 3 accounts, 21 plans, 76 days, 318 exercises and 246 sessions exactly.

18. Security tests

  • Ordinary account denial; explicit account-type validation; stable identity across workspaces; template isolation and crafted owner-route requests.
  • Pre-consent privacy; exact-code lookup; lookup throttle; self/stranger/other-coach denial; accept/decline ownership; disconnect and fresh-consent cycles.
  • QR hashes, expiry, replacement, GET non-consumption, single-use POST, replay and logged-out intended return.
  • Subscription owner/date/state checks, package snapshots and open-service uniqueness.
  • Assigned plan ownership, independent media, copy rollback, inherited custom identity and unauthorized library keys.
  • Attribution, service-date exclusions, stale previews and protection of manual/other-coach/saved/active/completed sessions.
  • Direct attempts to mutate trainee workout status, start/finish/discard, actual sets/weights, duration/calories or body weight are rejected.
  • Coach progression binds actor, relationship, subscription, assignment and existing evidence; paused/disconnected or cross-context requests fail.

The committed standalone MySQL concurrency check adds 17 assertions using two database connections under REPEATABLE READ. It tests an older transaction snapshot against a committed duplicate request, open subscription, used QR, pause/disconnect during plan/schedule/progression writes, and workout start/completion during session deletion. This is targeted isolation testing, not a load benchmark.

For future work, extend the current services and explicit coaching routes. Keep actual-workout writes owner-only. Avoid adding parallel history/progress engines or making workspace selection an authorization check. Any notification, billing or narrower consent feature should be a separate scoped update.

Before reopening a failed maintenance deployment, recover from the private pre-release backup or apply a verified forward fix. After users have written v1.6 data, do not blindly deploy v1.5 or drop coaching tables: older code does not distinguish coach templates. Prefer a forward fix that preserves new data.

26. Genuine remaining issues

No blocking defect remains from the completed automated, HTTP and browser checks. Verification is scoped to normal personal-training usage; it is not a high-load or independent penetration test. Physical phone-camera scanning remains unverified, although local SVG generation and the underlying token/request flow were exercised.

Intentional exclusions remain: billing/payments, marketplace, certification, organizations/teams, admin UI, messaging/comments/calls, push/email notifications, AI, nutrition, file sharing, social features, coach downgrade and an in-app camera scanner. Recent activity is a summary of current saved session states, not a permanent event stream. Existing legacy null-attribution sessions remain protected from coach management.
