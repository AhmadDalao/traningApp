1. Baseline version and commit

Built from v1.7.2, commit 4d436079fa155b40991ded5c9b6ee72599c2fc6e, on main. The brief names v1.7.1; the newer accepted baseline adds only the Profile card spacing fix, which is preserved.

Repository inspection found that the requested calendar features already existed in v1.7.0 and were deployed with v1.7.1. This release validates and tightens that implementation instead of building a second scheduler. Three focused runtime fixes and five additional PHP cases complete v1.8.0.

2. Architecture inspection

The application remains one Laravel / Inertia / React monolith, using Vite, MySQL and the existing FullCalendar interaction plugin. No dependency, authentication, layout or navigation replacement was necessary.

  • Reviewed PlanSchedule, ScheduleChangeController, ScheduleEntryController, TrainingPlanController, TrainingDayController, TrainingPlanDuplicator, CoachAccess, TrainingContext, policies, route middleware, models, migrations and the shared Calendar / Schedule UI.
  • Inspected actual local MySQL columns and indexes before changing code. Compared current source against prior release reports and tags.
  • Existing registration, onboarding, exercise library, supersets, active workouts, structured sets, History, body/exercise Progress, PRs, progressive overload, duplication and coaching remain in the regression suite.
  • No queue, Redis, cron, background daemon, separate API or Node production server.

3. Fixed and ongoing schedule modes

Fixed plans use real start/end dates. Ongoing plans require a start and allow a genuinely null end date. An optional end date stops an ongoing plan inclusively. No fake far-future dates. The shared period form is reused by personal plans, coach templates and assignments.

Saving configuration does not silently activate recurrence. Changed periods or weekdays require review and confirmation in Manage Schedule. Weekdays / Weekends / Every day / Clear retain the existing Friday–Saturday weekend convention.

4. Rolling-generation implementation

Only explicitly activated ongoing plans extend during normal Calendar / schedule actions. PlanSchedule::ensureWindow uses the existing user/plan/day locking and unique occurrence keys. It only adds missing eligible occurrences; removals require a signed, confirmed diff.

v1.8 improvement: automatic refresh loads relevant window bookings plus original keys whose occurrences were moved elsewhere. It no longer hydrates unrelated old workout rows. The regression fixture previously loaded 300 historical rows and now loads zero, while retaining all 300 in the database. Explicit user-requested schedule previews still include protected historical metadata.

Rolling cancellation lookup is restricted to the desired keys. No actual set payload is loaded by the scheduling query; snapshot and structured-workout existence remain protection flags.

5. Centralized rolling horizon

config/training.php supplies schedule_horizon_days = 90; PlanSchedule::horizon is the shared calculation. On 29 October 2026 the horizon is 27 January 2027. Plan stop dates and coach service dates further constrain generation. Repeated opening is idempotent; future generation happens on demand, not continuously while nobody uses the application.

6. Calendar date-click workflow

Click a day to see its existing sessions and Add another session. All entries on that date appear even if a Calendar filter hides them. An empty date opens the form directly. The selected date is prefilled; users choose a plan, then a day belonging to that plan, then optional time/title/notes.

Personal and coach-assigned plans are labeled with their source and coach. Owner and coaching scopes come from server queries. Manual extras never change weekly recurrence. Browser checks saved an extra session beside existing entries and verified an empty January date was prefilled correctly.

7. Desktop drag and mobile Change date

Existing FullCalendar drag support uses per-entry server permission flags. A drop immediately reverts visually and opens a confirmation form. Cancel persists nothing. Preview and Apply are separate actions. Event resizing stays disabled. Session Details retains Change date for mobile and explicit keyboard-accessible operation.

Browser checks exercised a real desktop drag, cancellation, preview, application and reload. Manual sessions show no recurrence selector. Generated sessions expose both supported scopes.

8. This session only

Only the chosen date/time changes. A generated occurrence retains its original plan_occurrence_key and becomes individually managed. Subsequent rolling generation and schedule reconciliation recognize it and do not recreate its original date. Next week keeps its base weekday. Tests also cover occurrences now in history or moved beyond the rolling window.

9. This and future sessions

The existing dated weekday phases change only the selected weekday stream from the effective occurrence. Other weekdays and previous dates remain intact. Moving Monday to Tuesday in a Monday/Wednesday/Friday workout produces Tuesday/Wednesday/Friday. Collision normalization avoids duplicate weekday rules; an intentionally moved session may coexist with an existing same-date session, with a warning before applying.

Fixed plans keep their end boundary. Ongoing plans use the revised rule during later window refreshes. ADD / KEEP / REMOVE / PROTECTED groups, signatures and current-state revalidation protect review-and-apply races. No new historical status/version system was introduced.

10. Recurrence exceptions

Moved occurrences reuse the existing occurrence key and unmanaged flag. The existing schedule_occurrence_cancellations table remembers deleted generated occurrences and suppresses regeneration. This table predates v1.8; no second exception model was added. Duplicating a plan/day copies reusable prescriptions, not occurrence history, exceptions, active sessions or activation state.

11. Stop Schedule

Manage Schedule exposes Stop schedule with a chosen date or Stop today. The inclusive date is retained; only later eligible generated occurrences may be removed after preview and confirmation. Manual extras, moved exceptions, completed/skipped/active/saved/historical entries and the plan itself remain.

v1.8 correction: a schedule stopped today or earlier no longer says rolling generation is active. It explains the stop boundary and how to restart through plan editing and review. Future-stop text displays the earlier of the plan stop date and 90-day horizon. The enabled flag can remain set so a future stop beyond today’s window still fills eligible intervening dates.

12. Coach scheduling

Coach Calendar reuses the same Calendar, plan/day form, schedule preview and reschedule controller, with explicit trainee route context. The logged-in actor stays the coach; session owner remains the trainee, and scheduled_by_user_id preserves attribution. Coach Personal Workspace continues to manage the coach’s own training normally.

v1.8 correction: the coach form no longer offers the standalone Rest day mode, which previously removed its assigned-day association and failed server validation. Coaches can still schedule rest days belonging to their own active assigned plan. This was verified through HTTP and the browser.

13. Subscriptions and relationship boundaries

Generation and schedule mutations require an active coach role/profile, accepted active relationship, currently effective active subscription and active assignment to that coach. Generated dates are bounded by inclusive service dates, including open-ended subscriptions bounded by the rolling horizon.

Paused, ended, expired, disconnected and ended-assignment cases now explicitly test both reschedule scopes and Stop Schedule at preview and application time. A valid earlier signature does not preserve access after revocation. Disconnection removes access without deleting trainee records. Existing accepted read access during paused/expired service remains unchanged.

15. Trainee self-coach restriction

GET and POST /profile/coach and switching to Coach Workspace remain forbidden for trainee accounts. Submitted role/profile flags cannot promote them. Existing coach registration and active coach profile editing remain supported. Lifecycle, feature and authenticated HTTP checks verified these restrictions; no upgrade button or role system was reintroduced.

16. Schema changes

None. Existing schedule_mode, schedule_enabled, schedule_actor_id, weekdays, schedule_rules, occurrence identity, managed state and cancellations already support the brief. No v1.8 migration or production database operation was performed. The existing v1.7 recurring migration remains unchanged.

17. Index inspection and query shape

No index added. Actual MySQL inspection confirmed the unique occurrence key, owner/date index, training-day foreign-key index, cancellation unique key, indexed structured-session lookup and coaching relationship/assignment indexes.

EXPLAIN on the actual bounded rolling query used the existing training-day and occurrence-key indexes, with a covering lookup for session_exercises existence. The date window and desired original-key exception predicate are owner/plan scoped. The query-count regression adds 40 visible sessions without per-session query growth. This is normal personal-training scale; no speculative index expansion was justified.

30. Known limitations and deliberate boundaries

  • Weekly weekday recurrence only; no monthly/ordinal RRULE, reminders, notifications, wearable or external-calendar sync.
  • Rolling generation requires normal application access and is capped at 90 days. No background job is scheduled.
  • This-and-future changes the chosen weekday stream; it is not a general recurring time/duration editor. Event resize remains disabled.
  • Multiple explicit sessions may share a date. Recurrence weekday normalization does not delete an intentionally moved same-date session.
  • Explicit Manage Schedule previews may read protected plan history so users can inspect what stays. Only automatic refresh was narrowed.
  • Existing owner-only historical individual editing behavior is retained; recurrence and coach operations have stricter protections.
  • Browser checks use viewport emulation; physical iOS/Android drag behavior was not tested. Change date provides the supported non-drag alternative.
