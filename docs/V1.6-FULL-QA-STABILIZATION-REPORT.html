Create future planned, completed and skipped sessions; open Personal or Coach Overview.

Create a planned session earlier today and another in the future; open a trainee card/detail.

Expected: Show the next unelapsed session.

Before: Earlier-today booking appeared as Next.

Cause: Date >= today ignored time.

Fix: Next-session queries use the shared upcoming scope and deterministic date/time/ID ordering.

StabilizationTest: trainee_cards; 320/390/1280 trainee views.

Medium		Last workout

Create a completed training session, then a later completed rest day.

Expected: Last workout identifies training.

Before: Rest day replaced the workout summary.

Cause: Completed status had no training-type condition.

Fix: Last-workout relation requires training and uses deterministic ordering.

Load 11 connected trainee cards with summary data.

Before: 26 data queries; two extra session queries per active trainee.

Medium		Subscription dates

Start service on 28 Oct in Asia/Riyadh; open My Coaching, trainee summaries or Assign Plan.

Expected: Show 28 Oct, matching subscription administration and permission dates.

Before: Some views showed 27 Oct.

Cause: Model only() returned Carbon midnight objects; JSON converted them to the previous UTC date.

Serialized-response regression across affected views; browser retest; two live date checks.

QA-06
Medium		Transaction/file cleanup

Inject a database deadlock after assignment media is copied and before assignment creation completes.

Before: Automatic retry replayed filesystem work and could leave orphaned copied media.

Cause: Database retry does not roll back file copies; cleanup only ran after the final failure.

Fix: Stop automatic replay in the shared coaching transaction; existing callers clean copied/uploaded files on failure.

CoachingTransactionTest: forced deadlock with real storage fake and full rollback/file assertions, on both databases.

Run isolated migrate/rollback through the library-and-schedule migration.

Accepted v1.6 consent explicitly allows a connected coach to view all of the trainee’s Calendar, workout history, Progress and PRs, including personal and other-coach workouts. The QA brief’s section 51 instead says opening another coach’s managed sessions must fail. Both rules cannot pass simultaneously. Existing consent behavior is preserved; no new read capability was introduced. The user has been asked to choose between preserving consent-based reads with cross-coach edits blocked, or narrowing those reads consistently across detail, History and Progress. This is a pending authorization-policy decision, not a claimed confirmed bypass of the current consent model.

Ending an assignment/subscription or relationship is allowed as an administrative revocation action where implemented; it does not delete training data. An ended relationship may still appear in its own coach’s administrative history, without granting trainee monitoring.

Queries, transactions, migrations and hosting

  • Trainee-list data queries measured 26 before → 6 after on the same 11-active-trainee fixture. A regression checks that adding trainees up to a full 12-card page does not introduce per-trainee queries. Only one next/last session per subject is eager-loaded.
  • Coach Overview limits its upcoming rows to 12 and recent statuses to 8. PR summaries reuse SQL workout aggregates for the bounded recent sessions; they do not load every SessionSet for every trainee. The existing implementation may repeat a bounded aggregate for recent sessions; no speculative redesign was added.
  • History loads the selected page and exercise/set counts. Exercise Progress aggregates per exercise/mode/workout in SQL; detailed sets are loaded only for the displayed workout-history page. Body Progress retains the existing personal-sized trend query.
  • Connection, subscription, assignment, schedule and disconnect mutations retain transactions and sorted user/parent locks. Two-connection tests verify current state after a competing commit for pause/disconnect, QR consumption and workout protection.
  • The deadlock regression confirmed why callbacks with filesystem effects must not be silently replayed. Existing catch/cleanup paths now run on failure; no partial plan/assignment or copied image remains.
  • The v1.6 migration is additive. Training Planner IDs are uniquely indexed and backfilled; session actor and assignment source links use null-on-delete where appropriate. Coach deletion cascades coaching administration, not trainee-owned plans, sessions or set logs.
  • Existing source-exercise-key and occurrence indexes were inspected/reused. No new indexes or tables were added. The only migration-file edit fixes an old down() operation; no migration or rollback ran on production.
  • The application still needs PHP, Laravel, MySQL/MariaDB and compiled Vite assets. No Node server, Redis, WebSocket service, Supervisor or queue worker was introduced.

Trainee ownership and historical preservation

  • Assigned TrainingPlan.user_id is the trainee; source template and assignment metadata do not transfer ownership to the coach.
  • ScheduleEntry.user_id is the trainee. scheduled_by_user_id only records the scheduling actor and becomes null if that coach is deleted.
  • SessionExercise and SessionSet belong through the trainee’s ScheduleEntry. Coaches never own or mutate those performance records.
  • Disconnect/end revokes access and ends administrative links without deleting assigned plans, Calendar entries, workouts, History, Progress, PRs or body-weight entries.
  • Deleting a coach account through the model/foreign-key path preserves assigned training, saved results and copied media. There is no new account-deletion UI in this update.
  • Template edits/deletion and applied progression leave historical snapshots and active prescriptions frozen. Current completion status remains the sole eligibility gate for Progress and PRs.
