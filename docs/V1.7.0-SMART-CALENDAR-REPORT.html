1. Summary

v1.7 extends the existing Laravel / Inertia / React application with maintainable weekly schedules. It reuses ScheduleEntry, FullCalendar, the v1.5 schedule diff, v1.6 coaching access, layouts and forms. There is no second calendar or recurrence engine.

Baseline: v1.6.1, commit 6f8379e. After the user’s go-ahead, implementation retained the accepted v1.6 consent: connected coaches may read the trainee’s full workout history, including other-coach sessions, but may edit only their own eligible assigned sessions. The previous QA policy hold is resolved on that basis; authorization was not broadened.

2. Schedule modes

ModeBehavior
FixedOptional unscheduled plan, or a start/end period. Existing one-year / 1,000-session preview limits remain.
OngoingExplicit mode, required start, initially null end date. Calendar generation starts only after a confirmed Manage Schedule action.
Stopped ongoingAn inclusive stop date is saved. If it lies beyond the current horizon, generation continues within the rolling window until that date. Renaming the plan preserves the stop date.

3. Rolling future window

The single setting config/training.php → schedule_horizon_days is 90. The upper bound is today + 90 days, further limited by a stop date and any active coaching subscription end date. For 28 October 2026, that is 26 January 2027. Today qualifies only when its specified time is still ahead; no past history is backfilled.

  • Opening Calendar or Manage Schedule ensures missing occurrences for explicitly activated ongoing plans. Refresh is additive: it does not replace or delete existing sessions.
  • A draft, duplicated plan or newly assigned plan is not activated by opening a page. The user first reviews and confirms the schedule.
  • Editing schedule-affecting plan/day settings, or copying/deleting a day, suspends automatic generation until another explicit review. Removing future sessions also disables automatic generation.
  • No cron, worker, Redis, WebSocket or Node production server is required.

4. Date-click scheduling

Click a Calendar date to see its existing sessions first, including sessions hidden by the current Calendar filter. “Add another session” opens the existing form with that date populated. Choose a plan, then only a day belonging to that plan. Plan labels distinguish Personal and Coach assigned, with the coach display name where available. Saving an extra session remains a manual action and does not change recurrence.

5. Drag/drop rules

Month and existing day-grid Week views allow eligible events to move. A confirmation dialog opens after a drag, while the temporary visual movement is immediately reverted. Cancel, validation failure and stale previews therefore leave the Calendar position unchanged. A successful request reloads authoritative data.

  • Only future planned, unstarted sessions without saved workout snapshots/structured results are eligible. Completed, skipped, active and historical sessions cannot use the new rescheduling endpoints.
  • The server rechecks ownership and coaching access. Event visibility is never treated as permission.
  • Event resizing remains disabled. The existing Week view is day-grid, not TimeGrid; duration is never inferred from event length.
  • Session Details → Change date is the mobile and keyboard fallback. This-session-only also supports changing its time.

6. This session only

The selected ScheduleEntry keeps its ID and original plan_occurrence_key. It becomes independent of bulk management using the existing schedule_managed=false flag. The weekly rule stays unchanged. Reopening Calendar and ordinary regeneration do not recreate the original keyed occurrence.

7. This and future

Available for an eligible, still-managed generated occurrence that matches its current weekly rule. The selected occurrence moves independently; the relevant weekday stream changes from that source occurrence onward. The preview shows its explicit move plus ADD / KEEP / REMOVE / PROTECTED groups for the other affected sessions.

  • Tuesday + Saturday → Wednesday + Saturday changes only Tuesday. Duplicate weekday rules are normalized.
  • Small dated weekday phases preserve the rule for earlier dates. They live on the existing TrainingDay; there is no generic recurrence framework.
  • A later destination can delay the replacement stream until that destination date. A destination before the source date moves the selected occurrence there, while the future rule takes effect from the original source date. Earlier sessions remain unchanged.
  • Existing sessions at the destination are retained; the confirmation warns about them. Multiple explicit occurrences may share a date, but generation does not create an additional duplicate occurrence key.
  • Fixed plans never extend past their existing end. Usual-time changes use the existing day editor and schedule review. Already individually moved occurrences offer this-session-only; Manage Schedule remains available for the plan.

8. Exceptions and cancellation

Moved occurrences reuse the existing key and independence flag. Deleting a generated occurrence records its original key in the small schedule_occurrence_cancellations table before deletion, so rolling generation does not recreate it. This also works through the existing Delete session flow; no second cancellation-status system was added. Unrelated manual sessions remain independent.

Cancellation markers are private to their parent plan, included in stale-preview signatures and removed when that plan is deleted. Copies do not inherit them. They reserve a logical date/key, not an unrelated weekday in a different recurrence configuration; future-rule previews show retained independent exceptions alongside proposed additions.

9. Stop Schedule

Manage Schedule → Stop schedule previews the inclusive last date, eligible later removals and protected records. “Stop today” is supported, including a plan that has not started yet. Only later eligible generated rows are removed; the plan, on-date sessions, manually edited exceptions and protected/history rows remain. There is no special pause/resume state machine. Clear the stop date in the normal plan editor, then confirm scheduling again when resuming.

10. Coaching behavior

The same controller/service and React modal serve both workspaces. A coach must have an active relationship, active effective subscription and active own assignment. Only their attributed future sessions can move or be removed. The trainee remains the owner. Template changes do not alter assigned copies, and assignment still requires a separate schedule review.

Automatic refresh retains the actor who activated the schedule. A trainee opening their Calendar does not turn coach-generated entries into personal entries. A coach viewing a trainee refreshes only schedules activated by that coach.

11. Subscription boundaries

Generation and drag destinations respect inclusive service dates. An open-ended active subscription permits the normal horizon. Paused, ended, expired or disconnected service, a deleted coach or ended assignment stops new coach generation; existing history and sessions are not silently deleted. These checks run again on apply and rolling refresh.

13. Additive schema and index review

  • Migration: 2026_10_28_000011_add_recurring_schedules.php. Existing plan rows default to fixed, inactive schedules with no actor; existing day rules default to null.
  • TrainingPlan: schedule_mode, schedule_enabled, nullable schedule_actor_id foreign key. Existing start/end fields are reused.
  • TrainingDay: nullable JSON schedule_rules containing dated weekday configurations.
  • One cancellation table: parent plan, unique occurrence key, created timestamp. No result/history schema changes.
  • Inspected real MySQL indexes before adding the migration. Existing occurrence-key unique index, training-day FK index and user/date index already support the queries. No duplicate indexes were added to existing schedule tables. New uniqueness/FK indexes belong only to the new data.
  • Local migration and full test migration/rollback paths pass. Original column hashes and new-field defaults were checked after QA.

Workouts are never logged or completed by the coach. JSON endpoints validate dates/scope, require confirmation and a signed preview for apply, use normal authenticated/CSRF-protected routes and do not accept ownership or actual-result mutations.

17. Idempotency and stale changes

Apply recomputes the preview under user/plan/day/session locks. HMAC signatures cover source state, proposed recurrence, affected rows, cancellation markers and coaching authorization context where applicable. Changed data requires a fresh preview. The existing unique occurrence key and first-or-create behavior prevent duplicate generation. Repeat apply cannot remove additional unrelated rows.

Four new two-connection MySQL checks pass: a concurrently started workout blocks a move; a concurrent completion invalidates Stop; rolling refresh sees a concurrently committed cancellation under REPEATABLE READ; repeated refresh after cancellation creates no duplicate. All 17 existing coaching concurrency checks also pass.

24. Release notes and delivery

Release tag: v1.7.0. Earlier v1.6.0 and v1.6.1 are preserved.

  • Added: explicit ongoing plans, confirmed activation, bounded rolling generation, date-first scheduling, desktop drag/drop, mobile Change date, this-occurrence / this-and-future previews, persistent moved/cancelled exceptions and Stop Schedule.
  • Preserved: fixed plans, existing weekday shortcuts, v1.5 diff, v1.6 coaching consent/ownership, manual extras, workout history, actual results, Progress/PRs and progression prescriptions.
  • Git push and tagging are the delivery requested in this turn. Hostinger remains on the deployed v1.6 stabilization code; v1.7 has not been deployed to production. A production deployment must include the new migration and frontend build while preserving environment and uploads.

25. Remaining scope and limits

  • No known unresolved defect was reproduced in the completed v1.7 checks. Production smoke tests have not been run because this release was not deployed to Hostinger.
  • Rolling refresh needs a normal Calendar / Manage Schedule visit; there is intentionally no cron or background worker. It does not fill dates that became historical while nobody opened the app.
  • No RRULE, ordinal monthly recurrence, event resizing, notifications, PWA, AI scheduling or v1.8 work was added.
  • The current Week view remains day-grid. Drag changes dates; usual recurring times are changed in the day editor with schedule review.
  • Individually moved or cancelled exceptions reserve original occurrence keys. If recurrence is deliberately changed to a different weekday, the explicit future diff can include additional new-rule dates while retaining those independent exceptions.
  • Shared-hosting production behavior still requires deployment verification; local PHP/MySQL and browser evidence is reported separately from production status.
