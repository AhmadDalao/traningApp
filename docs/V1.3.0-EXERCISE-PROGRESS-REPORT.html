1. v1.3 summary

Exercise Progress turns v1.2 structured workout logs into exercise-specific history, charts and Personal Records. The existing Progress page now links to a searchable performed-exercise list and detail pages. Finishing a detailed workout shows a compact PR summary and progress links.

v1.3.0 is deployed and tagged. Open the live application · View the release tag. This release extends the accepted v1.2.0 baseline, commit 8a7cab1, whose tag remains unchanged. No v1.4 work was started.

Before implementation, v1.2 passed 158 PHP tests / 3,327 assertions on SQLite and MySQL, 21 JavaScript tests and the production build. Its actual models, schema, indexes, controllers, tests and rendering were inspected. The local database contained 246 sessions but no structured set logs; no old history was converted.

5. Schema and index changes

One migration: 2026_10_27_000008_index_exercise_progress_identity.php. It adds a single-column index on session_exercises.source_exercise_key only when no existing index begins with that column. It is applied locally and on Hostinger. No columns, tables, snapshot formats or existing records were rewritten.

The existing unique (schedule_entry_id, position), source-training-exercise foreign-key index, schedule user/date index, and unique set (session_exercise_id, set_number) already cover their respective joins/orderings. None was duplicated.

Before migration, a local MySQL comparison using connection-local temporary tables with the actual schema/indexes and 300 sessions / 1,800 exercises / 5,400 sets measured the selected-identity query at 2.966 ms without and 0.459 ms with the single key index (medians). The indexed plan started from 36 matching exercise rows instead of walking 300 owned sessions. These are local query measurements, not production latency promises.

Final service measurements with the temporary browser dataset: overview used 2 queries / 3.716 ms median; detail used 3 queries / 2.550 ms median. SQL produces one aggregate per exercise/mode/workout. Only the current history page loads actual set details. No per-exercise N+1 query loop.

6. Exercise identity behavior

Aggregation uses the authenticated owner and the exact saved source_exercise_key. Different keys with the same name remain separate; renamed exercises with one key retain continuity. Missing/empty keys remain readable in workout history but do not aggregate. The UI explains this limitation.

One key logged in both Reps and Duration appears as separate progress entries. Names, icons and images come from the latest qualifying preserved session exercise. Deleting a plan, day, training exercise or custom-library item does not remove preserved performance. URLs pass the identity as an encoded query parameter, avoiding slash/colon route ambiguity.

7. Personal Record definitions

ModeRecords
Weighted repsHeaviest positive actual weight; Best Set = highest weight then most reps at that weight; Max Reps in one set with its positive recorded weight when available; highest exercise volume in one workout.
Reps without external weightMost actual reps in one completed set; most total completed reps in one workout.
DurationLongest completed set; longest total completed duration in one workout. Seconds internally, readable seconds/mm:ss on screen.

Records are all-time and derived from current data. New PRs compare strictly against earlier qualifying workouts, ordered by scheduled date, optional time, then session ID. Ties produce no new announcement. First qualifying measurement establishes a baseline. An increased weight does not also announce the same Best Set; equal weight with more reps can announce Best Set separately.

The overview shows the latest 8 PR events. Finish summaries group achievements by exercise and link directly to progress. These are historical results, never instructions to increase weight.

8. Qualification and volume rules

A result qualifies only when its session is currently completed and of type Training, the exercise is not skipped, the set has completed_at, and its actual result is positive reps or positive duration seconds for the saved tracking mode. Partially completed exercises contribute only their completed valid sets.

Weighted set = actual_weight_kg > 0 plus actual reps. Zero and null weights count for reps/history but never create Heaviest Weight, Best weighted Set, weighted volume or weighted chart points. No body-weight inference. No parsing planned prescriptions.

Workout exercise volume = Σ(actual positive kg × actual reps). No weighted sets means no weighted volume, rather than a fabricated zero. Decimal precision is preserved sensibly and displayed to at most two decimals. Example: 80×10 + 80×9 + 85×8 + 85×8 = 2,880 kg. Best Session Volume selects the maximum workout total, not the sum of all workouts.

9. Charts, dates and pagination

  • One point per exercise identity, tracking mode and completed workout, combining repeated occurrences of the same exercise within that workout.
  • Weighted charts: highest positive actual weight and total weighted volume. Reps-only: maximum completed reps per set. Duration: longest completed set.
  • Default 90 days; options 30 days, 6 calendar months, 1 year and All. Finite ranges include their start date and end today. All includes every qualifying completed workout, including a future-dated session if it was marked completed.
  • All-time PR cards remain unchanged when the chart/history period changes. Latest working weight means highest positive actual weight in the latest qualifying workout; blank if that workout has none.
  • Scheduled dates follow existing Training History/app timezone rules (Asia/Riyadh here). Date-only rendering avoids browser-timezone shifts. Same-day points are individually accessible through the Inspect workout selector, even when their SVG positions overlap.
  • Exercise list: 12 per page and name search. Exercise history: 10 workouts per page with the existing Pagination component. Filter changes reset pagination. Links reuse existing workout details.
  • One workout shows “First recorded performance.” Empty periods explain how to broaden the range. No structured logs means an honest empty state with Open Calendar.

17. Remaining issues and deliberate limits

No known blocking issue remains in the verified v1.3 workflows. Deployment, live verification and the v1.3.0 tag are complete.

  • Exercise Progress requires valid structured identity and actual logged sets. Old snapshots remain history-only; no backfill is possible without inventing data.
  • Library cards were left uncluttered; progress entry points are the Progress section and eligible completed-workout exercises.
  • The service derives records on read for normal personal-training usage. It does not cache results or support a speculative analytics workload.
  • Different modes stay separate. Duration exercises show duration metrics, with recorded positive weight still readable in their actual-set history. Weighted-reps history uses positive external weight only.
  • No 1RM, suggested next weight, automatic overload, automatic plan changes, muscle-group analysis, coaching, AI, nutrition or wearable integration.

Work stops at the verified v1.3 scope.
