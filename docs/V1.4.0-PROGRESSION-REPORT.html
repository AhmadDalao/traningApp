1. v1.4 summary

Implemented, verified and deployed on 28 October 2026. v1.4 adds a Next target card to Exercise Progress, using completed structured results to suggest an editable next weight, rep range or duration. Applying is always explicit. The existing Laravel + Inertia + React application, authentication, navigation and workout architecture remain intact.

Baseline: released v1.3.0 at 4054393. Released as v1.4.0 at training.ahmaddalao.com. Earlier release tags remain unchanged.

2. Progression rules

Suggestions use the latest two completed structured exercise occurrences belonging to the selected current plan exercise, exact stable identity, tracking mode and authenticated owner. Ordering follows scheduled date, optional time and session ID, matching Exercise Progress. A new copy in another plan needs its own two recorded workouts.

Recent unsuccessful occurrences remain in the two-workout window, including occurrences with zero completed valid sets. Skipped exercises and sessions currently Planned or Skipped are excluded. Recompletion uses final saved results. Quick completion and legacy snapshots never fabricate actual results. Only enough valid completed sets can satisfy the current planned set count; extra weak or incomplete sets do not make the requirement stricter.

Defaults are centralized: two workouts, +2.5 kg, +1 rep to both bounds, +5 seconds. Suggestions are derived on request; no jobs, caches, AI, external services or suggestion table.

3. Reps parser rules

One focused prescription helper accepts positive integers and simple ordered ranges, including 8, 8-10, 8 – 10 and 10-12 reps. Supported dash characters are normalized. Reversed ranges, zero, negatives, values above 10,000, AMRAP, failure, tempo instructions and compound prescriptions are rejected for automatic progression. Free-text prescriptions still work in the ordinary planner.

4. Duration parser rules

Duration mode uses a separate method in the same helper. Supported forms include seconds, minutes and mm:ss: 30 sec, 45 seconds, 1 min, 2 min and 1:30. Values normalize to seconds. Seconds in mm:ss must be 00–59; total duration must be 1–86,400 seconds. Bare numbers and ambiguous prose are not guessed. Applied values are saved in the existing reps/prescription field as seconds text.

5. Weight increase rule

For reps-mode templates with positive planned weight, both latest workouts must each contain at least the currently planned number of completed sets with actual weight at or above the planned weight and actual reps at or above the upper bound. Zero or missing weight never qualifies. A PR or one excellent set is insufficient. The suggested increase is +2.5 kg, editable before applying. Weight remains bounded by the existing 9,999.99 kg maximum.

6. Hold and build reps rules

Fewer valid completed sets than planned means complete the planned sets first. If too few sets reach the lower rep bound, build reps first. Enough sets inside the range without consistent upper-bound performance means hold. Recorded weight below the plan, or missing weight, blocks weight increases and is explained.

Unweighted and timed exercises use target-appropriate display text. Duration sets must each reach the planned seconds. No target increases beyond supported limits; the card explains when the next increment would exceed the limit. No automatic reductions or deload suggestions.

7. Template matching

Stable library identity and tracking mode find owned, current TrainingExercises on training days. Names alone never match. One match is preselected; multiple matches require selection before calculating. Each copy uses its own source_training_exercise_id history. A legacy null template mode retains the existing Reps meaning without a data rewrite.

Deleting a template leaves exercise history intact. When the latest frozen prescriptions agree and are parseable, a clearly labelled Historical suggestion can be viewed with no Apply action. Ambiguous or incomplete frozen prescriptions produce no current progression target.

8. Apply behavior

The existing modal shows the selected plan/day/exercise, current value, suggested value and editable proposed target. The backend rereads the template and relevant history inside a transaction, compares a signed fingerprint of the evidence and recalculates eligibility. It shares existing user, training-day and parent-session locks with the workout/editor flows. Locking evidence reads see the latest committed data even under MySQL REPEATABLE READ.

Stale submissions refresh the suggestion without writing. If the identity changes, the obsolete selection is cleared; if no completed results remain, the user returns to the exercise list with an explanation instead of a 404. Duplicate requests cannot apply an increment twice: the endpoint assigns a validated value, never current + increment.

Only the selected target_weight or reps field changes. Other copies, sets, notes, snapshots, active prescriptions and history stay unchanged. Fresh future starts naturally capture the latest template. Previously frozen, reopened sessions retain their saved prescriptions. Completed workout exercises include a View next target link.

11. Schema and query review

No migrations, new tables, backfills or new indexes. The current database already indexes source_exercise_key and, on MySQL, the source_training_exercise_id foreign key. The inspected progression query uses the existing source-template index, joins owned completed sessions and limits occurrences to two before loading their sets. No successful-set prefilter can hide a recent failed attempt.

The local MySQL EXPLAIN used source_training_exercise_id plus the existing user/date session index. One selected-target read took five queries and 2.84 ms of database time in the small temporary QA fixture; this is a spot measurement, not a production performance promise. Normal personal-training scale requires no additional indexing.

12. Authorization and validation

All routes require authentication. Existing TrainingDay ownership policy protects writes; matching and history reads are owner-scoped. Tokens bind the user, target, configuration and recent saved evidence. Another plan copy or forged token cannot reuse a suggestion. Server-side validation checks weights and uses the same centralized prescription parser for edited reps/duration. The shared limits preserve existing planner and set-log validation behavior.

19. Remaining issues and deliberate limits

No blocking issue remains in the verified implementation. The verified release is deployed; source and release documentation are published under v1.4.0. The local accounts currently contain no original structured workout logs, so recommendations appear after detailed workouts are recorded; old history is not backfilled.

Suggestions are specific to each current plan exercise and require two recorded occurrences. Unparseable free text has no automatic advice. Historical fallback is read-only and requires consistent, supported frozen prescriptions. Optional list indicators and a general suggestions summary were left out to keep the requested core flow simple. There is no AI, estimated 1RM, fatigue/recovery scoring, RPE/RIR, automatic adaptation, background notifications or suggested weight reduction.
