Architecture

One Laravel application with a React interface. Inertia connects Laravel routes and controllers to React pages. Authentication, database access, validation, and permissions stay in Laravel. This structure is suitable for the next planned feature stages.

1 · React interface

Pages, forms, modals, exercise pickers, and FullCalendar. Inertia handles navigation and submissions.

2 · Laravel application

Routes → validation and ownership checks → controllers/services → Eloquent models.

3 · Persistent storage

MariaDB stores accounts and training data. Filesystem storage holds uploads and preserved workout media.

LayerCurrent technology
BackendLaravel 12 / PHP; PHP 8.3.36 recorded on Hostinger at deployment.
FrontendReact 19, Inertia 2, Vite 6, FullCalendar 6, Lucide icons, and application CSS.
DatabaseMySQL-compatible schema; production uses MariaDB. SQLite and MySQL were used for test verification.
AuthenticationLaravel session authentication. No separate public API or token-based mobile authentication.
HostingHostinger PHP hosting. Frontend assets are compiled locally; no Node server, queue worker, or ongoing recurrence scheduler is required for current features.

Keep this architecture for the next phase. Add focused modules to the existing app. A separate API becomes useful if native mobile apps or external integrations become actual requirements.

Training History: a filtered view of scheduled sessions
TableMain responsibility
usersAccount identity, hashed password, and remember token.
training_plansUser ownership, name, description, and optional plan dates.
training_daysPlan ownership, training/rest type, focus, icon, notes, ordering, weekdays, and usual time.
training_exercisesDay ownership, name, sets, text reps/duration, target weight, superset group, media paths, library key, and ordering.
exercise_library_itemsUser-owned custom exercises and their independent media. Built-in exercises are not rows in this table.
schedule_entriesUser ownership, optional template link, scheduled date/time, status, notes, completion timestamp, saved workout JSON, and a unique generated-occurrence key.

There is no separate history table. Calendar, Overview, and Training History read the same session records. Completion adds a versioned workout_snapshot to that session. Actual weights live inside this snapshot; the template retains its target weights.

Deleting a plan or day removes its exercise templates. Scheduled sessions remain with their basic details, and completed sessions retain their saved workout and copied images. An uncompleted session whose template was deleted cannot reconstruct those exercises.

Rules future updates must respect

  1. A workout template and a completed workout are separate records. Editing a plan must not rewrite completed history. First completion freezes the prescription and copies its media; optional actual weights remain editable.
  2. History filters use the scheduled date. Completion time is stored separately. History includes previous dates and today's sessions once their optional time has passed; date-only entries for today are included. Future sessions are excluded.
  3. Calendar and History share data, but not filter state. Selecting Today in History does not navigate Calendar. Changing a session status is reflected wherever that record is shown.
  4. Scheduling is explicit and finite. Saving plan dates or weekday choices alone does not add sessions. Preview and confirm to generate today/future occurrences. Preview limits are one year and 1,000 sessions. Later edits do not automatically move or delete existing sessions.
  5. Rest is a session type. Planned, Completed, and Skipped are statuses. Rest days do not count as completed training workouts.
  6. Supersets belong within one workout. They are stored as shared group strings on exercises. Choosing from the library creates a workout exercise before linking it; a superset does not link two calendar sessions.
  7. Time and units are shared settings today. The app uses Asia/Riyadh and kilograms. Dashboard weeks run Monday–Sunday, while the requested Weekdays shortcut is Sunday–Thursday.
  8. Plans are not per-set logs. Sets are a count; reps or duration are text. Actual weight is one optional value per exercise. Exact completed reps, durations, and weights for each individual set are not captured.

Recommended next development stages

The items below are proposals, not implemented features. Prioritize reliable daily use before adding advanced training analysis.

1 · Build on the release baseline and add account essentials

Build future changes from the v1.0.0 baseline, document a repeatable deployment/rollback process, and establish scheduled backups with a restore check. Add password reset, profile/password editing, and an account settings page. Current login/register/logout is complete, but account recovery is missing.

Touches: authentication routes/controllers, account pages, mail configuration, deployment documentation. A simple automated browser smoke test would complement the existing PHP and JavaScript tests.

2 · Make everyday planning faster

Add duplicate plan/day, a dedicated page to manage custom exercises, favorites/recent exercises, and clear controls to update or remove future generated sessions. Define whether each schedule change affects one occurrence, future occurrences, or the entire remaining plan before implementing it.

Touches: plan/day controllers, ExerciseLibrary service and picker, PlanSchedule, Calendar. Preserve completed records and manually moved sessions.

3 · Add structured workout logging

Introduce an active-workout view with actual reps, duration, weight, and completion per set; then add a rest timer and optional effort rating. Use explicit session-exercise and session-set records if set-level reporting becomes a requirement. Keep existing version-1 snapshots readable.

Decision first: what should a user record during a workout? The present free-text reps/duration and exercise-level weights are insufficient for exact set-volume calculations.

4 · Add progress and exports

Build exercise progress, personal records, consistency charts, and CSV/PDF exports. Establish a stable exercise identity across library, templates, and saved workouts; completed snapshots currently preserve exercise details but not the library key. Start with completion and exercise-weight trends; exact volume needs the structured logs from stage 3.

Touches: history queries, snapshot versioning or session-log tables, reporting pages. Historical records cannot supply measurements that were never recorded.

5 · Choose the product direction

For personal use, consider reminders, an installable mobile experience, and calendar integration. For a coaching product, add coach/client roles, explicit assignments and sharing permissions, then messaging and billing if needed. Decide the audience before designing shared ownership.

Not currently built: coach/admin dashboard, plan sharing, notifications, payments, AI programming, native mobile apps, offline sync, or an external API. Per-user timezones, preferred weight units, and private media delivery would also be new capabilities; uploaded images currently use public storage URLs.

Next release recommendation: account recovery and settings, duplicate plan/day, and custom exercise management—alongside a committed release baseline and repeatable backups. These improve everyday use without changing the existing application structure.
