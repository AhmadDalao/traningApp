1. v1.5 summary

v1.5.0 adds independent plan/day copies and explicit management of finite future Calendar sessions. The existing Plan → Schedule → Train → Record → Progress → Apply workflow remains one Laravel + Inertia + React application, one repository, and one database.

The accepted baseline is v1.4.0 (fd64a18). New actions are Duplicate Plan, Duplicate Day, Copy to Plan, Manage Schedule, Add Missing Sessions, Remove Future Sessions and Regenerate Future Schedule. Scheduling changes always require preview and confirmation.

v1.5.0 is deployed, verified and published under its release tag. Original accounts, workouts, uploads and credentials are preserved.

5. Schema changes

One additive boolean: schedule_entries.schedule_managed, default false, migration 2026_10_28_000009_add_schedule_management_guard.php. No new tables, indexes, keys, backfill of workout history or change to actual results.

The existing unique plan_occurrence_key reliably identifies generated origin, but does not record whether an old session’s time was individually edited. Newly generated v1.5 occurrences opt into management. Existing rows stay independent, with the default false value. An individual Calendar edit opts a generated occurrence out while preserving its original key. This single flag avoids guessing about older edits.

Inspected indexes include the unique occurrence key, training-day foreign key and user/date index. These are sufficient for the owned plan/day/date query at normal personal-training scale; no duplicate index was added.

6. Duplicate Plan behavior

Creates Original Name — Copy, then Copy 2, Copy 3 and so on, within the 150-character Unicode limit. The user does not need to enter a name first. It copies description, finite plan dates, all training/rest days in their original order, weekdays and usual times, exercise ordering and prescriptions, weights, sets, reps/duration, tracking modes, supersets, icons, notes, stable library identities and independent media files.

It copies no Calendar sessions, snapshots, actual weights, structured session exercises/sets, active workouts, history, PR records or progression state. The result is an ordinary unscheduled plan. Its period and weekday preferences are ready for an explicit preview. Copies preserve the stable exercise identity for general Exercise Progress, but v1.4 progression eligibility still requires the new plan exercise’s own structured history.

7. Duplicate Day behavior

Creates an independent day in the same plan, appending it after the current final day. Naming uses — Copy, Copy 2, etc. Type, focus, notes, icon, weekdays/time, exercise order and prescriptions are copied; existing superset letters remain grouped within the new day. New exercises have new database IDs and retain their library identities.

Media follows the existing independent-file convention. Deleting or editing the original cannot remove the copy’s files or change its prescriptions. If a media copy fails, the transaction and newly created files are rolled back. No Calendar session is copied.

8. Copy-to-plan behavior

The existing day actions open a destination-plan selector listing only the signed-in user’s other plans. Server authorization checks both the source day and destination plan. The copied day is appended to the destination and is independently editable; source data remains unchanged. A user with no other plan gets a clear instruction to create a destination first.

The copied weekday preferences may affect a future desired schedule, so the app offers Review Schedule or Not now. It does not silently generate sessions.

9. Schedule diff rules

CategoryMeaning
ADDFuture desired occurrences with no existing reservation; also explicitly identified replacements for changed usual time or training/rest type.
KEEPEligible generated sessions that already match the desired occurrence time/type.
REMOVEEligible generated sessions that no longer match the plan, including the old side of a time/type replacement.
PROTECTEDManual/independent, completed, skipped, started, saved or historical sessions. They are never changed by these bulk actions.

Desired dates reuse the finite plan period and weekdays: at most a one-year period and 1,000 desired occurrences. Future means after today, or today with a specified time later than now in the application timezone. Today’s untimed/elapsed sessions are preserved, matching the existing History boundary.

Add Missing adds only missing occurrences. It does not replace an existing time. Regenerate adds missing occurrences and optionally removes obsolete eligible sessions; checking that option also permits reviewed time/type replacements. Replacements reuse the original occurrence key inside the transaction. Remove Future explicitly lists and removes all eligible future generated sessions, including matching ones; preferences remain available for a later generation.

10. Generated/manual session identification

The existing identity remains plan:{plan_id}:{day_id}:{date}. The database’s existing unique constraint remains the final duplicate guard. A manual session has no occurrence key and cannot claim generated status through client input. The original key is retained after individual edits, so a moved occurrence still reserves its original place and is not generated twice.

The pre-existing day/date booking rule also remains: a manual or protected session on a desired day/date prevents another occurrence for that date. Older generated sessions appear as independent protected rows because their previous time-edit history cannot be proven. They remain editable/deletable individually through Calendar.

11. Protected-session behavior

Bulk actions protect any session whose current status is Completed or Skipped, any non-null started_at, any saved workout snapshot or structured exercise rows, all historical dates/times, and all manual/independent sessions. Even an unstarted Planned session with saved structured data is protected. Started workouts retain their schedule and frozen prescriptions.

Changing plan dates, weekdays, usual time or day configuration only saves the reusable plan and shows a dismissible review notice. Editing one Calendar session only changes that session. Applying a v1.4 progression suggestion changes a prescription, not the schedule; schedule management never changes planned weight, reps, duration or other exercise fields.

12. Idempotency and concurrency

Each preview carries a signed fingerprint of the current plan rules, occurrences and classifications. On confirmation, the server checks ownership, takes user/plan/day/session locks, rereads current data and validates the fingerprint. If a plan/session changes or an occurrence crosses the time boundary, the action is rejected with a refreshed preview. A replay cannot add unpreviewed sessions or delete a newly protected workout.

Repeated successful generation followed by a fresh preview makes no extra changes. Replaying the old changed preview is safely rejected. Existing occurrence keys and the unique index remain the only duplicate-prevention identity. Calendar creation and Active Workout start share the user lock; existing parent-session locks serialize status, logging, updates and schedule management.

A separate two-connection MySQL check established an older REPEATABLE READ snapshot, committed a completion from the other connection, then attempted removal. Current locking reads rejected the stale preview and preserved the completed session.

19. Genuine remaining issues and limits

No known blocking issue in the verified v1.5 implementation. Older generated occurrences are intentionally protected from bulk management because their past individual time edits were not recorded. Manage those individually in Calendar; newly generated untouched sessions support all v1.5 bulk actions. This is a safety limit, not a guessed migration.

Schedules remain finite. Unspecified times on today’s date are historical; the app never invents a time. A copied plan keeps dates/preferences but starts unscheduled. A manual edit remains independent and is not silently brought back into bulk management.

No infinite recurrence, background scheduler, automatic Calendar mutation, drag-and-drop, AI, recovery/deload logic, RPE/RIR, reminders, PWA, wearables or coaching was added. Work stops at v1.5.0.
