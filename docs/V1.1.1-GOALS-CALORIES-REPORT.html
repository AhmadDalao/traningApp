1. Patch summary and release notes

Users can select up to two goals, mark one Primary and the other Secondary, switch priority, and see recommendations explained against their actual preferences. Completed training sessions can receive a server-calculated calorie estimate based on duration, intensity and body weight. Reported values remain independent and take display priority.

Added

  • Maximum-two goal selection in the existing onboarding and profile forms, with an inline limit message and Make primary action.
  • Combined-goal recommendation adjustments and explicit reasons, using the existing six presets.
  • Session-level estimated calories, three intensity levels, historical weight selection, and separate reported calorie sources.

Changed

  • Manual Calories Burned is now labelled Reported Calories. The underlying column is unchanged.
  • History uses reported calories when present, otherwise an approximate estimate, otherwise a dash.
  • Optional details PATCH requests preserve omitted values. Explicit null clears duration or reported calories.

Not included

No AI, wearable API, nutrition, daily calorie targets, BMR/TDEE, per-exercise calories, per-set logging, notifications, coaching, exports, or new Progress dashboard.

2. Multiple goals and recommendation behavior

training_goals is nullable JSON, ordered and limited to two distinct existing goal keys. Index 0 is Primary; index 1 is Secondary. Zero goals remains valid because onboarding/profile setup stays optional. One goal does not require a secondary choice.

["build_muscle", "lose_fat"]

Reads prefer a nonempty list, then fall back to [training_goal]. Profile/onboarding saves synchronize training_goal with Primary. Clearing all goals also clears the legacy value. Existing single-goal clients can still save, producing a one-item list. No profile is rewritten merely by reading it; existing onboarding state is preserved.

Primary drives the original preset ranking. Secondary adds a smaller preference and adjusts supporting work. Existing experience/day/equipment restrictions still apply. BMI, body-weight targets, and equipment never become inferred goals.

The existing full-body preset offers Bodyweight Strength & Conditioning — 4 Days when strength/muscle is primary, fat loss/endurance is secondary, at least four days are available, and gym/dumbbell equipment is unavailable. Its four focuses are Upper Body, Legs, Full Body and Cardio. No seventh preset or separate recommendation architecture was added.

Cards and details list Primary, optional Secondary, equipment access, experience, actual workout count against available days, and intended session duration. Alternatives are identified as alternatives. Nothing is copied until Use this plan; copied plans remain editable and unscheduled.

3. Calorie formula and MET assumptions

The backend-only WorkoutCalorieEstimator calculates:

round(MET × 3.5 × body_weight_kg / 200 × duration_minutes)

The result is an integer kcal estimate for the whole session. It is never calculated per exercise or accepted from React input.

Saved session focusCategoryLightModerateVigorous
Cardiocardio4.06.08.0
Mobilitymobility2.02.53.0
All other / unset focusesstrength3.03.56.0

These are the approximate MET assumptions specified for this patch, not medical measurements. Constants and focus mapping live in one backend class. For 80 kg, 50 minutes and moderate strength, the result is ≈245 kcal; vigorous strength is ≈420 kcal.

Eligibility and weight selection

  1. The session must be completed and of type training, with actual duration.
  2. Use the latest owned BodyWeightEntry with recorded_date on or before scheduled_date. Highest ID breaks same-day ties.
  3. If none exists, use profile current_weight_kg. Usable values follow the existing 20–500 kg range.
  4. If weight/duration is missing, or the session is rest/planned/skipped, no estimate is generated.

Duration follows the existing 1–1,440 minute integer range. Intensity defaults to Moderate when editing new details or first calculating without a saved intensity. None of these inputs is required for one-click completion.

Historical stability

Reading pages, changing profile/body-weight history, changing recommendation logic, and changing constants do not automatically rewrite stored estimates. Saving reported calories alone preserves an existing estimate. Editing duration/intensity recalculates. Explicit changes to scheduled date or saved focus/type also recalculate eligibility against the updated session. Notes-only edits preserve the estimate.

Changing status to Planned/Skipped clears the estimate because the session is ineligible. Completing again can create a new estimate using retained duration/intensity and the weight-selection rules. Reported values and workout snapshots remain retained through the existing reversal flow. No background backfill is run.

Reported versus estimated

calories_burned remains reported calories, including a valid zero. Sources are wearable, exercise_machine, and manual. Existing null source values display as Manual entry; existing manual records stay manual. Clearing reported calories nulls both that value and its source, without removing a valid estimate.

Details show reported calories first with their source, and a secondary App estimate. With only an estimate, the primary value uses ≈ and Estimated. History shows one number. The form displays the stored server estimate; unsaved duration/intensity edits ask the user to save before an updated estimate appears. There is no frontend calculation.
